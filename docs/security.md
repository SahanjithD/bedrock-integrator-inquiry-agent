# Security notes

This sample shows a pattern. It is not production ready. Review these points before you adapt it.

## Data

- All data is synthetic. Names, email addresses (`example.com`), reservation numbers and card
  endings are made up.
- The guardrail masks names, email addresses, phone numbers, addresses and card numbers in
  the model's output, so findings and draft replies stored on the case are masked. Input is
  checked but not changed, so tool results reach the model intact. Card security codes are
  blocked in both directions. Check the guardrail's behavior with your own data.
- Resolved-case summaries in the knowledge base are built from masked findings and the write
  tool's response. Review what your own write tools return before you ingest it.

## Identity and access

- Each component has its own IAM role with only the actions it uses.
  - The inquiry listener's ECS task role can consume the two queues, read and update the case
    table, and invoke the agent runtime with a runtime user ID. It cannot call the model, the
    knowledge base or the gateway.
  - The inquiry agent's AgentCore execution role can call the model with the guardrail, retrieve
    from and add to the knowledge base, and get gateway tokens from its two AgentCore Identity
    credential providers. It has no access to SQS or DynamoDB.
- The agent runtime uses IAM (SigV4) inbound auth. Only the listener's task role may call it.
- The listener tasks have no inbound ports. Their security group allows outbound HTTPS only.
- The gateway accepts Cognito client-credentials tokens from two clients: the investigator
  (read scope) and the applier (write scope). The MCP runtimes accept tokens only from the
  gateway's outbound client.
- Client secrets are generated by Cognito and handed to AgentCore Identity credential providers
  by the deploy scripts. The agent never holds them: it exchanges the workload access token
  AgentCore Runtime gives it for an access token. The execution role may read only the agent's
  own two provider secrets, not the gateway's. No secret is in an image, a runtime's environment
  or `BAL_CONFIG_DATA`. The listener needs no secrets.

## Changes and approvals

- The model never calls a write tool. It can only propose one, and the proposal is checked
  (known write tool, required arguments, IDs from the evidence, no self-supplied approval ID).
- The decision message carries no action. The listener reads the stored proposal from the case
  and sends it to the agent.
- Conditional updates make sure a proposal is applied at most once per approved version. A
  retry with an unknown outcome stops at `NEEDS_REVIEW` for a person to check.
- Write tools are idempotent per `approvalId`.
- The support portal runs on the reader's machine with their AWS credentials. It has no sign-in
  and does not record who approved. In production the support system would authenticate
  representatives, record the approver, and enforce who may approve which change.

## Not covered

- Gateway-side authorization of individual tools by scope (for example with an interceptor or
  AgentCore Policy).
- Encryption with customer managed AWS KMS keys (AWS owned or managed keys are used).
- Private networking. The listener task runs in a public subnet with a public IP, and the
  agent and MCP runtimes use public network mode. For production, use private subnets with VPC endpoints.
- Prompt injection hardening beyond the read-only design and proposal checks. Guest messages
  are untrusted input.
